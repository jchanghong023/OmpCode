# OmpCode 真实桌面端到端测试

本文是给 AI 执行的模拟人工验收规程：按下述步骤操作真实桌面、观察结果并保存证据，不要求新增或改动现有测试脚本。

本专项作为项目“基本可用”的核心验收。全部通过后，可判定报告绑定版本在 Windows 桌面、指定模型下的核心使用流程基本可用；验收覆盖范围以本文件为准，未涉及的平台与功能不据此标记为通过。

产品规则仍分别由 [模型与配置](models-and-commands.md)、[子代理与集成](integrations.md)、[Agent 交互页](agent-interactions.md) 和 [会话恢复](session-recovery.md) 维护。本文件只维护跨功能的验收步骤；既有 [三级测试门禁](test-gates.md) 独立保留。

## 一、测试目标

在 Windows 环境中，对 OmpCode 进行真实 GUI 端到端测试，验证数据隔离、模型配置、持久化、主代理与子代理执行、文件操作、广播通信及界面显示。

测试必须通过真实 OmpCode 桌面程序完成，模拟用户鼠标点击、键盘输入、页面切换及重启操作，不允许只通过 RPC 或单元测试代替 GUI 验收。

优先使用独立虚拟桌面或隔离桌面会话，避免抢占用户鼠标和键盘。

执行前确认 AI 能截图、点击和输入到本次测试实例。Windows 虚拟桌面本身不等于独立鼠标/键盘会话；缺少可用的隔离操作方式时如实记录条件，不假设工具可以操作隐藏窗口。实际无法操作测试实例时记为 BLOCKED。

## 二、测试环境隔离

1. 按项目指令检查 Git 仓库、分支、工作区状态，并阅读 AGENTS.md 和相关需求文档。
2. 为本次测试创建独立临时测试根，使用唯一名称，禁止与现有测试目录或用户目录冲突。OMP 根、工作区和证据目录分别放在该测试根内，例如 `测试根/omp`、`测试根/workspace`、`测试根/evidence`。
3. 使用当前测试进程专属的临时环境变量 `OMP_CONFIG_ROOT`，将 OMP 配置根指向上述 `omp` 目录的绝对路径。
4. 确认 OmpCode 数据根自动派生为 `<OMP_CONFIG_ROOT>_ompcode`，即示例中的 `测试根/omp_ompcode`，属于 OMP 根的兄弟目录。应用设置、索引和日志位于其 `v2` 子目录，Electron 数据位于其 `electron` 子目录；OMP 原始会话与子代理记录仍按 OMP 根/profile 解析，不能误认为全部位于 `_ompcode`。
5. 环境变量只对测试进程及其子进程生效，不修改 Windows 全局或用户环境变量。
6. 启动独立 OmpCode 实例，不连接、复用、关闭或修改用户正在运行的实例。
7. 测试使用专属工作区，所有文件操作限定在该工作区。
8. 如现有 E2E 启动器不兼容 "OMP_CONFIG_ROOT"，采用安全的独立启动方式，不能简单删除其隔离检查。
9. 记录实际生效的 OMP 根目录、OmpCode 数据目录、工作区及进程信息，并验证它们没有指向真实用户数据目录。
10. 核对测试子进程继承的 `OMP_PROFILE`、`PI_PROFILE`、`PI_CODING_AGENT_DIR`、`PI_CONFIG_DIR`、认证来源及 `OMP_RPC_ARGS_JSON` 等覆盖项。只在测试子进程环境中移除或替换会破坏隔离、强制其他模型或思考等级的值；不能仅设置 `OMP_CONFIG_ROOT` 就认为其他覆盖项必然安全。
11. 用唯一应用身份启动本次实例；开发态如需远程调试，使用专属空闲端口，并关闭默认固定调试端口。保存测试 PID 与进程树，退出和重启仅处理这些进程。启动前确认所运行应用对应本次源码或所记录安装包；开发态运行时与依赖以 `mise.toml` 为准。

## 三、复制 OMP 认证信息

1. 确认真实 OMP 使用的认证数据库、认证文件及其实际位置，不假设固定文件名。
2. 从真实 OMP 配置中只读获取认证数据，安全复制必要的认证信息到临时 OMP 配置根。
3. 如认证使用 SQLite，采用一致性快照或安全备份方式，不能直接复制正在写入的不一致数据库。
   当前 OMP 本地认证存储使用 `getAgentDbPath()` 解析的 `agent.db`，该库也承载非认证数据。快照仅作为临时中间件，从中提取目标 Provider 必需的认证记录到隔离存储，不把整个库当成纯认证文件沿用；实际使用远程认证等其他来源时按其真实机制处理。
4. 保留必要的文件权限，不复制无关的会话历史、缓存或角色模型配置。
5. 认证信息不能写入测试日志、截图、报告或 Git 仓库。
6. 如果复制的 OAuth 凭据可能发生刷新令牌轮换、影响真实 OMP 登录状态，必须使用不会破坏真实登录状态的安全方式，不能冒险测试。
7. 从隔离 OMP 运行时确认 OpenAI Codex 认证有效、目标模型可以使用。
8. 不允许为了使测试通过而关闭认证检查、绕过安全验证或切换其他模型。

整个测试过程中不得修改真实 OMP 的认证数据库和配置文件。

检查认证时不得对真实根调用可能自动刷新并回写认证的命令。复制 OAuth 数据不代表与远端刷新状态隔离；无法证明测试不会使用共享刷新令牌影响真实登录时，在调用模型前记录 BLOCKED。不要通过关闭刷新、安全校验或认证检查继续执行。

## 四、GUI 配置主代理和 Task 模型

通过 Computer Use 操作真实 OmpCode GUI：

1. 打开 OmpCode。
2. 进入设置 → 模型设置。
3. 确认当前运行的是隔离 OMP Profile。若在 GUI 中切换了 Profile，先保存并完全重启本次测试实例，再继续角色编辑；待重启期间不能编辑旧 Profile 的角色。
4. 找到 "default"（主代理默认角色）。
5. 配置：
   - Provider："openai-codex"
   - Model：GPT-6 Luna
   - Reasoning/Thinking："high"
6. 找到 "task"（子代理角色），配置为完全相同的模型和思考等级。
7. 等待两项配置自动保存。
8. 关闭并重新打开模型设置，检查选项正确显示。
9. 读取隔离 OMP 的实际角色配置文件，确认 "modelRoles.default" 和 "modelRoles.task" 已更新。
10. 验证其他配置字段、未修改角色和相关注释没有意外变化。

当前 GUI 的模型下拉菜单按 Provider 分组，不要求存在单独的 Provider 表单。选择 `openai-codex` 分组中的目标模型，再选择 `high`；配置保存必须以成功状态和实际配置读回为准，不用固定等待时长代替。保存前记录配置基线，保存后核对实际生效文件和字段。

模型 ID 必须以 OMP 实际模型目录为准。如果 GUI 中没有 GPT-6 Luna，或该模型不支持 High，不允许擅自替换模型或降低思考等级，应明确记录测试阻塞。

本地 OMP 源码目录中对应标识为 `openai-codex/gpt-6-luna`，角色持久值应解析为该模型及 `high`，当前格式为 `openai-codex/gpt-6-luna:high`。源码目录存在该项只能证明目录定义，不能代替隔离运行时的可见性、账号权限与真实调用成功。

必须区分会话临时模型选择与持久化 Role 配置。不能只修改当前聊天模型就认为角色配置成功。

## 五、重启验证模型配置持久化

1. 完全退出测试 OmpCode 实例及其子进程。
2. 保留同一个临时数据根及测试配置。
3. 使用相同环境变量重新启动独立 OmpCode 实例。
4. 再次通过 GUI 打开模型设置。
5. 确认 "default" 和 "task" 仍为 OpenAI Codex / GPT-6 Luna / High。
6. 重新读取 OMP 角色配置文件，确认保存结果没有丢失、回滚或被其他配置覆盖。
7. 在重启后新建的测试会话及后续三个子代理中，分别验证运行时实际使用目标模型和 `high`；此项随第七节真实任务完成，不提前假设已经生效。确认没有会话临时选项、启动参数、代理类型或项目配置覆盖角色。

以上任一条件不满足，模型配置持久化测试失败。

## 六、准备文件测试工作区

在独立临时工作区中创建以下三个预置文件：

- "a1"，内容为 "old-a1"
- "a2"，内容为 "old-a2"
- "a3"，内容为 "old-a3"

文件名均不带扩展名。

记录创建前后实际文件清单和工作区绝对路径。

预置文件用于验证子代理能够发现已有文件，并明确先删除再创建，而不是简单覆盖。

文件计数统一定义为：测试工作区顶层的普通文件数量，不递归统计子目录。记录任务启动前的基准数量。

预置和最终文件统一使用 UTF-8、无 BOM、无末尾换行；最终分别只有两个字节 `a1`、`a2`、`a3`。工作区、证据与运行配置目录分开，避免报告文件进入计数。路径检查须解析到真实位置，不能通过链接、junction 或重解析点越出测试工作区。

发送任务前确认当前 OMP 能使用异步、非阻塞的 `task` 子代理与真实通信；三个代理使用通用 `task` 类型，继承 `@task`，共同操作本次工作区。确认没有启用会把文件写到另一个工作树的任务隔离，没有模型/思考覆盖。必要的准备只作用于隔离配置，记录角色编辑前基线；条件不满足时记为 BLOCKED。

## 七、通过 GUI 发送真实测试任务

新建 OmpCode 会话，选择上述临时工作区，通过 GUI 输入框发送以下提示词，不允许直接通过 RPC 注入任务。

### 发送给主代理的完整提示词

```text
请使用真实 OMP 子代理功能完成以下任务。

当前工作目录为本次会话工作区。所有文件操作必须限定在这个目录，禁止操作其他目录。

1. 一次分配三个并行子代理，分别命名为 Agent1、Agent2、Agent3。每个子代理只负责一个文件：

   - Agent1 负责 "a1"，内容为 "a1"
   - Agent2 负责 "a2"，内容为 "a2"
   - Agent3 负责 "a3"，内容为 "a3"

2. 每个子代理先独立统计当前工作目录顶层普通文件的数量，记录实际统计结果。建议先完成计数与通信，再进行文件操作。

3. 使用 OMP 的真实子代理通信功能向三个子代理发送一次广播，要求每个子代理返回自己负责的文件名及统计的文件数量。使用真实子代理 ID，不得通过普通聊天文字假装发送。不要求广播与其他运行事件的精确先后或时间间隔。

4. 三个子代理收到广播后，分别向主代理发送实际通信消息，说明负责的文件名及统计结果。使用真实代理 ID，不允许伪造消息。

5. 主代理协调三个子代理完成各自文件操作，建议收齐计数回复后通知开始创建。每个子代理分别独立执行：

   - 检查自己负责的文件是否存在。
   - 如果存在，必须先明确执行删除操作。
   - 然后创建同名文件，内容必须与文件名一致。
   - 文件使用 UTF-8、无 BOM、不添加末尾换行。
   - 读取文件，验证文件内容正确。
   - 向主代理报告完成结果。

6. 每个子代理完成读取校验后，用 OMP 的真实结果提交机制（当前为 yield）提交最终成功或失败，不把普通回复或等待指令时的空闲状态当成任务完成。主代理确认全部三个子代理的真实结果，最终用正常自然语言总结：三个子代理名称、各自负责的文件、统计数量、广播与回复情况、文件创建结果。

要求真正调用 task、通信和文件工具，保留完整执行过程。不能通过主代理直接创建三个文件代替子代理执行，也不能只输出模拟的工具调用记录。
```

### 功能验收边界

- 使用一次批量 `task` 分配三个子代理，允许实际启动存在调度差异；验收三个真实身份、各自执行与最终结果。
- 验收真实广播、实际接收者和三条回复的存在、归属及内容，不验证 OMP 消息精确时序、到达顺序或时间差；上述计数后协调创建属于执行建议。
- 文件数量按各代理实际计数记录展示，不要求因并发而不同的计数完全相同；仍核对计数对象是同一个测试工作区的顶层普通文件。
- 当前 OMP 的真实通信入口为 `write` 到 `agent://all`（广播）或 `agent://<真实ID>`（定向消息），不是写一个同名磁盘文件。回复发给当前实际主代理 ID；代理消息自动送达，不指示没有自己后台任务的子代理反复调用 `wait` 等待父代理。
- 主代理的成功总结必须有三个子代理实际完成的依据。任务结束以结构化结果和运行事实判断，不要求每个子代理会话对象被销毁。

## 八、主代理 GUI 验收

通过 Computer Use 观察并操作主代理界面：

1. 用户提示词正确发送并显示。
2. 主代理开始执行，没有卡死或异常报错。
3. 界面真实显示三个子代理，能区分其名称和运行状态。
4. 子代理运行状态随实际执行进度变化。
5. 主代理的广播操作可以找到真实执行依据。
6. 主代理能够收到三个子代理的文件名和统计结果。
7. 子代理完成后，主代理状态恢复正常。
8. 最终回复为完整、可读的自然语言，不出现仅有 JSON、协议消息、空白输出或未处理异常的情况。
9. 最终文字与真实执行结果一致，不允许把失败或未完成任务描述成成功。

## 九、子代理 GUI 验收

依次点击三个子代理，进入各自详情界面。

每个子代理都必须验证：

1. 子代理名称、任务、目标文件正确。
2. 可以查看真实工具调用过程。
3. 可以看到文件数量统计操作及结果。
4. 可以查看接收到的广播消息及发送给主代理的回复。
5. 可以看到已有文件检查记录。
6. 可以看到先删除旧文件，再创建新文件的工具执行记录。
7. 可以看到读取文件验证内容的过程。
8. 工具参数、执行结果、错误信息及运行状态正确显示。
9. 子代理完成后，界面显示正确的完成状态。
10. 切换子代理详情不会混淆其他代理的日志和工具记录。

不能只根据最终文件存在，就判断子代理执行过程正确。

必须证明三个文件分别由对应的真实子代理创建。

## 十、子代理交互界面验收

通过 GUI 打开子代理交互页面。

检查：

1. 能正确显示主代理与三个子代理。
2. 代理层级和名称正确。
3. 能查看主代理广播消息。
4. 能查看三个子代理分别回复的消息。
5. 消息方向、发送者、接收者及内容与真实记录一致。时间仅作为页面展示信息，不核验 OMP 消息时序或精确时间；缺失时间应按原功能规则显示未知或记录时间。
6. 点击代理或消息，可以查看详细记录。
7. 通信关系、连线和选中状态正确，不发生错位或重叠遮挡。
8. 子代理较多或日志较长时，页面仍可滚动，文字可读。
9. 切换页面、关闭并重新打开交互页面后，记录仍然正确。

检查时将 GUI 内容与可取得的 OMP 实际会话、子代理和工具记录交叉验证，不能只检查 DOM 中存在对应文字。当前 OMP 没有统一全量持久通信日志，不能假设存在专门的完整审计库；本场景需要的广播和回复若在实时或重启后缺少对应真实记录，明确记录失败与缺口，不补造证据。

对关键界面保存截图，结合页面元素、实际工具记录和文件结果判断是否符合预期。

## 十一、最终文件验收

使用测试程序直接检查临时工作区：

| 文件 | 预期内容 | 负责代理 |
| ---- | -------- | -------- |
| a1   | a1       | Agent1   |
| a2   | a2       | Agent2   |
| a3   | a3       | Agent3   |

验收条件：

- 三个文件均存在，且内容精确匹配。
- 旧内容 "old-a1"、"old-a2"、"old-a3" 已不存在。
- 三个子代理各自有对应的删除、写入及校验工具调用证据。
- 文件创建路径均属于独立测试工作区。
- 三个子代理均真实运行完成。
- 没有无关文件或用户数据被意外修改。
- 主代理的最终文字回复与实际文件和子代理执行记录一致。

## 十二、测试后重启恢复验收

完成任务后再次完全退出测试 OmpCode。

使用相同临时配置和工作区重新启动：

1. 检查主代理与 task 角色模型配置仍然正确。
2. 检查测试会话能够恢复。
3. 检查主代理最终回复仍可查看。
4. 检查三个子代理的历史记录及工具执行过程仍可查看。
5. 检查子代理交互页面的通信历史可以恢复。
6. 检查三个文件及内容仍然正确。
7. 检查界面没有错误地将已完成的代理显示为正在运行。

恢复的是原测试会话和三个原子代理 ID，不创建新会话替代，也不重新发送任务。冷恢复检查只读进行，不发起新的模型轮次。

## 十三、安全与执行原则

- 不修改真实 OMP 和真实 OmpCode 的配置、数据库或会话。
- 不触碰真实项目中的业务文件，所有删除操作只允许在临时测试工作区中执行。
- 不能删除、覆盖已有的非测试临时目录。
- 不修改系统环境变量，不终止用户已有进程。
- 不将认证信息、Token、Cookie 或 API 密钥输出到报告。
- 不为通过测试而更换模型、伪造广播、注入模拟子代理结果或跳过失败步骤。
- 优先通过 GUI 完成交互，通过文件、进程及 RPC 只读检查补充验证。
- 视觉操作优先运行在独立桌面会话中，避免抢占用户鼠标和键盘。
- 如发现产品缺陷，记录复现步骤和证据，不擅自修改业务代码。
- 测试失败时保留必要日志、截图、执行证据和临时目录，方便后续定位。
