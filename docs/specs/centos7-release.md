# CentOS 7 x64 release (native, dedicated branch)

## Product behavior

- `experiment/centos7-no-proot` is the long-lived CentOS 7-only release branch; it is not merged into `main`. Its native glibc-2.17 ZIP runs on Linux 3.10 without PRoot, an Ubuntu userspace, root access, host package installation, network access, or replacing the user's installed omp. Verify the complete application in the CentOS 7 VM before changing the GitHub release workflow; only the proven branch may be used to build the manual `-centos7` ZIP/checksum release.
- The self-contained ZIP with its SHA256 checksum is the only CentOS 7 distribution format. Do not produce or restore any RPM or installer that embeds a PRoot/Ubuntu userspace or requires one to run (the earlier `OmpCode-3.14.3-centos7-x64.rpm` belongs to the abandoned PRoot design). PRoot is permitted only as a development/packaging convenience (running Node/pnpm inside an Ubuntu userspace on an old-glibc host); it must never appear in, or be referenced by, any shipped artifact or user-facing launch path.
- This branch pins Electron 28.3.3, Node 18-compatible dependencies, and CentOS-compatible native addons directly in its manifests and lockfile. Electron 29.4.6 requires GLIBC_2.18 and Electron 30.5.1 requires GLIBC_2.25 on the tested VM, while the official Electron 28.3.3 binary opened a rendered window as the non-root `roo` user.
- The archive includes the app, embedded omp, compatible `node-pty`, SSH through `ssh2` and Electron's built-in crypto, and native search executables, plus any private glibc-2.17-compatible C++ or GUI libraries/fonts required for an offline launch. The Linux desktop renderer must supply its own redistributable Simplified Chinese glyphs when the host has no CJK fonts; the fallback must cover settings, menus, conversation text and code, and retain the font license in the ZIP. Do not ship `ssh2`'s optional `sshcrypto.node` accelerator: Electron 28 uses OpenSSL 1.1.1, whereas the glibc-2.17 Node 20 builder provides OpenSSL 3 headers; a loadable accelerator built against those headers fails during SSH key exchange. It does not bundle or replace glibc. A binary that requires newer GLIBC symbols must fail packaging, not become a runtime surprise.

- This dedicated branch owns the runtime selection, ELF compatibility checks, dependency versions, ZIP layout, symlinks, permissions and checksum. The launcher sets process-local paths for libraries and private XDG settings, resolves its installation directory, selects the omp startup profile and offline mode, and starts the bundled Electron directly.
- The app and package tooling build with the repository's Node 24/pnpm toolchain; native modules and search executables compile separately on a glibc-2.17 x64 builder using pinned Node 20.19.0 (glibc-217 build) and GCC 11. Node 20 is build-only and is not shipped in the ZIP. The native stage must be merged into `app.asar`/`app.asar.unpacked` and `resources/tools`, not copied beside the Electron executable.
- The dedicated CentOS 7 desktop distribution disables its Internet features by default, regardless of `--offline`. Only the embedded omp can use its own configured enterprise API endpoints. The embedded browser can open enterprise intranet documents (including DNS names resolving only to private addresses). Other desktop HTTP(S)/WebSocket traffic is confined to loopback. Enterprise SSH workspaces remain usable. Do not add an internal-hostname allowlist for desktop services. Public configuration, help, telemetry, CDN, account and external-browser flows must not run. The desktop Main/Renderer and Host own this policy; the embedded omp retains its normal network behavior unless explicitly passed `--offline`. The launcher accepts `--profile <name>` or `--profile=<name>` and an optional `--offline`, rejects missing or invalid profile names before starting Electron, and forwards other launch arguments unchanged. An explicit launch profile overrides the saved App Settings profile for this run. Only embedded omp children receive `--offline` when requested.
- Recommended prompts must refer only to local tasks and bundled icons, with no public site, online plugin or downloaded image required. Remove unused public animation assets. Delete online account, subscription, share, marketplace, bot, feedback, telemetry and public configuration paths and UI entries. Omp owns model and skill configuration and the enterprise API; the UI must use its existing omp integration instead of the former ZCode plugin marketplace. The prompt catalog is owned by the UI and never performs network IO; the launcher remains the desktop network-policy owner. A missing optional visual must not delay or block rendering.
- Cleanup boundary: on the CentOS 7 desktop, Help and native menus contain no online documentation, community, feedback, or feature-request actions. The root UI does not restore or poll a ZCode OAuth account; no plugin-marketplace action or cloud-share flow is offered. Main does not schedule app launch/daily-active telemetry or forward remote-usage/session-create reports, and Host does not start or admit online bot work. Existing shared protocol types and Web-only code are not product entries. The launcher-owned local-only flag is independent of omp's optional `--offline` flag; blocked actions fail without a public request. Verify both startup and user-triggered paths, preserving local resource management, omp skills, SSH, and the embedded intranet browser.
- The launcher accepts `--home <absolute-dir>` to put all OmpCode-wide persistent and temporary data below that directory before Electron starts. It creates `<absolute-dir>/.ompcode` and `<absolute-dir>/.omp`, links `~/.ompcode` and `~/.omp` to those directories, places Electron user/session data plus XDG config, data, cache, state and temporary directories below `<absolute-dir>`, and creates the app's default/scratch workspaces there. `PI_CONFIG_DIR`, `ZCODE_DATA_BASE_DIR` and `ZCODE_DESKTOP_HOME_DIR` also point below the selected directory; the shell's `HOME` remains unchanged for SSH and other user environment files. A saved data directory or a Settings change cannot override an explicit `--home`. Reusing existing links to the same targets is idempotent. Existing directories or links to other targets are preserved and cause a clear error; managed paths inside the selected directory that resolve outside it are rejected. The launcher never moves or deletes existing data. Relative paths, missing values, `--home ~` and destinations inside `~/.ompcode` or `~/.omp` are rejected. Without `--home`, startup retains the existing data locations.
- Host utility processes use dedicated stdout/stderr pipes so their logging cannot inherit invalid descriptors from a Citrix or shell session. If a raw output pipe becomes unavailable (`EBADF`/`EPIPE`), logging continues over the existing structured message channel without terminating the Host; unrelated write errors remain visible. The CentOS 7 release workflow requires the dedicated branch and an unused tag but imposes no custom tag naming pattern. An empty tag input generates `v<app-version>-centos7-<run-id>-<run-attempt>`; a supplied tag is preserved if valid and unused. The build job publishes its resolved tag as a job output, and the publish job uses exactly that value. A rerun gets a different automatic tag.
- Creating or updating a release targeted at this dedicated branch requires the repository secret `OMPCODE_RELEASE_TOKEN`: a fine-grained personal access token for this repository with Contents and Workflows write permissions (or an equivalent GitHub App installation token). GitHub Actions' default token cannot obtain Workflows write permission while this branch changes `.github/workflows/` relative to `main`. Fail before the expensive build if the secret is absent; use the secret only in the publish job. Keep the release tag targeted at the workflow commit rather than the default branch.
- The manual release workflow may reuse its CentOS 7 native staging directory across runs on the dedicated branch. The cache key must cover the lockfile, native build scripts, search-tool source/config/verification scripts, Electron package version and pinned toolchain workflow; use only exact cache hits, and rebuild on misses. Restored native assets must still pass existence and ELF checks, and the assembled ZIP must still pass the full compatibility, SSH, archive and checksum checks before publishing. Never cache the final release ZIP or an unpacked desktop application.

- Electron's `ELECTRON_RUN_AS_NODE` child executes the existing omp adapter; omp retains ownership of configuration, sessions and credentials in its config directory (the default `~/.omp`, linked below `--home` when selected). The embedded omp remains distinct from any user-installed executable. The launch path does not use `ptrace`, bind mounts or `OMPCODE_CENTOS7_BIND`; working directories are ordinary host paths.
- Electron 28 embeds Node 18.18.2, while this app uses newer Node APIs (including `fs/promises.glob` and `node:sqlite`). Supply real equivalents for those paths and compatible dependency versions without downgrading user-visible features. Electron 28 also lacks `webUtils` and `webContents.navigationHistory`; replacements must preserve file attachment and browser history behavior rather than silently disabling it.
- Rootless extraction cannot install Chromium's setuid sandbox. The launcher uses `--no-sandbox`; this is an explicit security limitation, especially with an end-of-life Electron/Chromium version. A graphical X11/Wayland session remains required. A server missing XKB/GLX may still fail independently of glibc compatibility.
- Runtime libraries must not silently load from the builder's newer OS. The ZIP must preserve executable modes and symlinks; relocation must not break launch. Missing required resources and incompatible ELF dependencies fail before distribution. The packaging stage also runs a loopback SSH handshake with the packaged Electron runtime on an ephemeral port; it does not replace the CentOS 7 VM acceptance.

## Acceptance

- On the CentOS 7 x64 VM (`glibc 2.17`, kernel `3.10.0-1160.el7.x86_64`), a non-root user extracts the ZIP under HOME without installing anything, starts the launcher and sees the OmpCode UI. With no CJK host fonts, Chinese settings and menu labels and arbitrary Chinese conversation text display as glyphs rather than empty boxes; English remains legible. Exercise a real embedded omp session, the integrated terminal and native search; complete an SSH handshake with the packaged `ssh2` client and verify the optional native crypto accelerator is absent from both `app.asar` and `app.asar.unpacked`.
- Launch with a named `--profile` that differs from the saved App Settings profile: bundled omp receives that profile, while the UI's roles and history read the same named profile. Launch with `--offline` to pass it to each bundled omp process; omit it to leave omp's ordinary network behavior intact. A missing or invalid profile name exits with a clear error before Electron starts.
- Without `--offline`, trace network connections while starting the desktop, opening settings, showing recommended content, and using the embedded browser: Main, Renderer, Host and scheduler never connect to public hosts; the embedded browser opens a corporate DNS name resolving to a private IP and rejects a public URL; only omp may reach the configured enterprise API. With `--offline`, verify the same desktop boundary and verify that omp receives its offline flag.
- Inspect the bundled recommendation catalog and UI assets: every recommendation can run with local tools, every recommendation icon is bundled, and no animation source points at a public host.
- Launch with `--home` pointing to an empty directory outside the default data path: `.ompcode`, `.omp`, XDG, Electron user/session, cache, state and temporary paths resolve below the target; `~/.ompcode` and `~/.omp` link to the matching target directories; the shell `HOME` is unchanged. A saved data directory is ignored and cannot be changed outside the target while the override is active. A second launch with the same destination succeeds without changes. An occupied `~/.ompcode` or `~/.omp`, a conflicting link, an escaping managed-directory symlink or an invalid destination exits without replacing user data. Without `--home`, the launcher's existing XDG defaults and other environment paths remain unchanged.
- A closed or invalid Host stdout/stderr descriptor cannot turn an ordinary RPC log into an uncaught exception; structured logs still reach Main. The release workflow accepts an unused short custom tag such as `v0928` or generates one when left blank, and still rejects a reused tag or the wrong branch. Automatic tags differ across workflow reruns.
- Inspect every shipped executable and native addon for GLIBC requirements <= 2.17 and ensure its C++ runtime is provided if the host's `libstdc++` lacks the required symbols. The release ZIP contains neither PRoot nor an Ubuntu root filesystem. It does not modify the host's glibc or existing omp installation. Only after this VM acceptance passes, update the manual CentOS workflow to build from `experiment/centos7-no-proot`.
- The company Citrix X Server is a separate acceptance environment. Passing the VM's X11 display does not imply that the company server's XKB or GLX capabilities work.
